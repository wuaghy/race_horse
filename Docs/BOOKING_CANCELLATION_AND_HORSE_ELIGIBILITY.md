# Booking cancellation and horse eligibility

Customers can cancel their own requests in `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, and `NEED_INFORMATION` with `POST /api/v1/transport-requests/{requestId}/cancel`. The request body is `{ "reason": "optional text" }`; the reason is capped at 1000 characters. The command is idempotent, locks the request row, preserves any manager assignment, and appends a `CANCELLED` audit transition with the prior status.

For an approved request, use `POST /api/v1/orders/{orderId}/cancel` with the same body. Booking verifies ownership, queries Planning over internal gRPC, and permits cancellation only when no trip exists or the trip remains `PLANNED`. A still-planned trip is cancelled when Planning consumes `Booking.OrderCancelled`. Planning and Booking do not share a transaction, so a trip could move to READY between the read and Booking write; the event handler retains the advanced trip state and logs the mismatch. A later saga or shared cancellation command is needed to eliminate that race.

Booking checks horse status at both submit and approval; every selected horse must be `ACTIVE`. It also enforces a conservative one-open-transport rule: a horse cannot be in another nonterminal request or order. A request counts as open through `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, and `NEED_INFORMATION`; an approved order counts until Booking observes trip completion or the order is cancelled. This intentionally prevents a second future request while the first is open because Booking does not own route-trip intervals. The guard is rerun under locks at submit and approval.

The wizard can query `GET /api/v1/transport-requests/horse-availability?horseIds={guid}&horseIds={guid}` with optional `requestId` for an owned editable draft. It returns one `{ horseId, eligible, horseStatus, blocker }` item per requested ID, without revealing horses the customer does not own. This is guidance; submit and approval remain authoritative.

Compliance document requirements remain owned by Compliance. Booking queries its internal checklist before submit. Active route rules' required Horse-scope documents apply at the departure date; when no applicable Horse-scope rule exists, the baseline is an approved, valid-at-departure HORSE_PASSPORT and VACCINATION_CERT for each horse. Customer checklist reads show `ready` and one item per required horse/document type. Documents must have been uploaded by the customer identity that owns the request.
